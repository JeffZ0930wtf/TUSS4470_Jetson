# V1.0.1 release notes

## Document overview

This document records the V1.0.1 source/software release, its launcher changes,
and the scope of release verification. It supplements the
[V1.0.0 artifact manifest](v1.0.0-manifest.md) and
[known limitations](v1.0.0-known-limitations.md), which continue to define the
accepted acquisition runtime and physical-hardware evidence.

## Release scope

- Software version and annotated Git tag: `1.0.1` / `v1.0.1`.
- Previous release: `v1.0.0`, resolving to `d5ba025ddd0da450c5ea2ab31ca4c9152dbd44d7`.
- Launcher implementation: `3b83ee7eccf007992244ae0e9d9db065a848f1ff`.
- Windows entry: `scripts/start-jetson.ps1`, which invokes the Jetson script
  through SSH, establishes or reuses a local tunnel, and opens the browser.
- Jetson entry: `scripts/start-jetson.sh`, which starts Core/Bridge through
  Compose, checks readiness, and opens a desktop browser when available.
- Both entries require explicit external 7 V confirmation. They do not Apply
  configuration, request acquisition, or intentionally generate a Burst.
- The launchers finish after startup; runtime supervision is not added.
- Windows PowerShell launcher tests are scoped to Windows so they do not
  require Windows PowerShell in the native Jetson test suite.
- The release includes the V1.0.0 documentation corrections and the recorded
  waveform vertical-axis presentation limitation.

## Operating limits

Existing Compose restart policies are unchanged. The script's explicit supply
confirmation applies to script invocation; it does not add a new gate to Docker's
automatic container restarts. Readiness is a startup observation, not continuous
power monitoring. Follow the supply/reset procedure in the deployment guide.

Windows tunnel reuse recognizes the existing project's HTTP health/device
response; it does not prove the existing tunnel's destination matches a changed
host argument. Use distinct local ports when switching between Jetson hosts.

The startup timeout is a polling deadline, not a strict deadline around every
external command. An unresponsive Docker/HTTP operation can delay completion.
Browser invocation is best-effort on Jetson; a Windows browser-launch error can
still be reported after the remote services and tunnel have become ready.
