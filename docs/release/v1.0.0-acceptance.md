# V1.0.0 acceptance summary

## Document overview

This document summarizes the evidence accepted for the TUSS4470 acquisition
module V1.0.0 release. It answers which Windows, Jetson, hardware, storage, and
data-integrity claims are supported. Detailed chronological evidence remains
under `docs/archive/pre-v1/verification/`; this summary does not replace those
records or broaden the claims in them.

## Accepted scope

- Configuration covers all supported TUSS4470 GUI device fields and the
  acquisition/run parameters exposed by the shared schema.
- A real capture contains exactly 2048 unmodified 16-bit envelope samples and
  the configuration, run plan, event, quality, device, boot, and request
  metadata needed for later peak, TOF, energy, attenuation, multi-peak,
  correlation, and frequency-domain analysis.
- Core, Bridge, REST, CLI, Web, SQLite, save policies, periodic/STOP/lease,
  synchronization, events, and single-field sweep were exercised on Windows
  and/or real Jetson hardware as recorded below.
- The module stops at acquisition and output; SOC/SOH prediction and acoustic
  feature computation are intentionally outside V1.

## Accepted Windows and firmware evidence

The exact V1 candidate `3642f45905f1ec3113d89d693ee827df1aa71e74`
completed 231 Python tests plus the Node Web regression, MSP430 simulator,
TI USB-stack build, formal firmware build, and all retained static safety
checks without serial access, flashing, or Burst. The native Windows Core also
completed configuration apply/readback, single capture under `SAVE_NONE` and
`SAVE_ALL`, finite periodic and single-field sweep under `SAVE_LAST`, history,
and offline export after Core stopped. The exported `.usac` and `.u16le` files
matched the corresponding `CaptureRecord` BLOBs byte-for-byte.

Earlier real Windows acquisition evidence includes exact 2048-point
frames, SQLite commit closure, zero pending spool after acknowledgement,
configuration endpoints, finite/periodic operation, and long sequences of 2,
100, 1000, 9604, 3823, and 9460 requested captures. The accepted long runs
retained continuous committed sequences and fixed 4096-byte sample BLOBs and
4324-byte wire frames; scheduling limitations are stated separately.

## Accepted Jetson evidence

The same source, protocol, schema, migrations, and firmware `0.2.0.2` ran on
JetPack 7.2.1 / Jetson Linux 39.2.1 / ARM64. The ARM64 Core/Bridge stack passed
real identity, configuration readback, finite capture, periodic completion,
STOP, lease expiry, all IO modes, sample/Burst endpoints, Pulse 1/2/63,
Master/Slave synchronization, event reporting, sweep, all save policies,
offline private-network startup, restart persistence, and raw-byte identity.

The accepted Slave capture `fabe00644d8f16a721734d93e174315c`
contains 2048 samples, a 4096-byte sample BLOB, a 4324-byte wire frame, and its
full run plan in SQLite. Bridge pending returned to zero after Core commit.

231 Python tests, Node Web regression, C protocol vectors, native ARM64 image,

## Release boundary

This evidence supports a bounded experimental V1.0.0 acquisition module. It
does not establish calibrated timing, lossless long-term scheduling,
production security, or unattended product reliability. Those limits are
normative in [V1 known limitations](v1.0.0-known-limitations.md).
