# M3 采集帧传输与产品化扩展设计

## 文档说明

本文档定义 M3 将一次完整超声采集从 MSP430 内存可靠输出到 Windows/Jetson
主机的传输设计，解决 `CAPTURE_DATA` 在连续 64 字节应用层发送后静默中断的
问题。它适用于 M3 首条真实波形及后续采集传输演进，是 `docs/protocol.md`
的实现约束补充；主机诊断依据仍记录在
`docs/m3-host-capture-diagnostics-design.md`。本文档不修改 TUSS4470 配置、
ADC/DMA 时序、原始数据格式或 BMS 数据处理边界。

## 目标顺序

本设计同时服务两个时间尺度，但优先级明确：

1. 当前必须在不增加硬件风险的前提下跑通一条 200 kS/s、2048 点、
   `Pulse=1` 的真实原始波形；
2. 当前实现必须建立稳定的传输状态边界，使后续加入周期采集、交付确认、
   重传、诊断和 bridge spool 时无需改变采集数据格式或推倒 USB 发送层；
3. 当前不提前实现成熟产品才需要的完整可靠交付机制。

“可扩展”在本文档中指已定义接口、状态和不变量，不代表 M3 已经实现未来
功能。

## 现场证据与问题定位

修正 DMA 完成状态报告后，设备能够返回 `CAPTURE_ONCE` ACK 和合法的
`CAPTURE_DATA` 帧头，帧头声明完整帧为 4324 字节。这证明 2048 点采集已经
通过固件完整性门禁，故障位于采集完成后的输出路径。

第二次实测在帧头之后准确收到 128 字节，即两个 64 字节应用片段，随后连续
静默超过 5 秒。主机已经采用有界读取和按进度刷新的静默超时，因此固定总
时限不是该次失败的根因。

当前发送器在应用层把所有区域切成不超过 64 字节，并对每片独立调用 TI
`USBCDC_sendData`。TI CDC 库本身已经按 64 字节 USB Bulk 端点包进行内部
分包，并对以 64 字节满包结束的独立发送处理零长度包。连续建立大量恰好
64 字节的应用发送事务增加了完成事件、零长度包和下一事务启动之间的状态
交接。现有流迭代器还会在 `USBCDC_sendData` 确认启动前推进偏移；若接口
短暂返回 BUSY，该段已经在逻辑上被消费，现有代码只能结束会话，主机最终
表现为无错误帧的静默超时。

该根因判断必须以修改后的完整 4324 字节真实帧作为最终确认；在此之前不得
把 M3 宣告为完成。

## 当前 M3 传输架构

### 帧与 USB 事务分层

`CAPTURE_DATA` 在线协议中仍是一条连续的 4324 字节帧，应用内存由四个
生命周期稳定的区域组成：

```text
CAPTURE_DATA wire frame (4324 B)
├─ protocol header     16 B
├─ capture metadata   208 B  (188 B fixed fields + 20 B register snapshot)
├─ raw ADC samples   4096 B  (2048 × uint16 little-endian)
└─ frame CRC            4 B
```

M3 将这四个区域分别作为四个应用层发送事务交给 TI CDC。TI CDC 在每个事务
内部完成 64 字节 USB 包化。64 字节是 USB 端点实现细节，不是线协议分块，
也不再是应用层发送事务上限。

样本仍直接来自唯一的 4096 字节波形缓冲，不建立第二份样本副本，不插值，
也不为发送重新编码采样值。

### 可提交的发送状态机

发送器必须把“查看下一段”和“确认该段已经交给传输层”分开。建议状态为：

```text
IDLE
  ↓ prepare frame
READY(segment 0)
  ↓ transport accepts
IN_FLIGHT(segment 0)
  ↓ send-completed event
READY(segment 1)
  ↓ ...
IN_FLIGHT(segment 3)
  ↓ send-completed event
COMPLETE
```

必须满足以下不变量：

- 只有 `USBCDC_sendData` 返回 `USBCDC_SEND_STARTED` 后，当前段才可标记为
  已启动；
- 只有对应发送完成事件到达后，才可提交当前段并推进到下一段；
- `USBCDC_INTERFACE_BUSY_ERROR` 不得推进段索引、不得结束采集会话，也不得
  重新采集；发送器保留同一地址和长度，待接口可用后重试启动；
- 总线不可用、DTR 下降、USB 复位或无法恢复的 CDC 错误必须终止传输会话，
  使硬件回到安全状态，并留下可诊断的失败原因；
- 一次采集在发送完成或明确终止前不得被新采集覆盖；
- 传输重试只能重发内存中同一帧，不得隐式执行第二次 Burst。

### 主机接收

主机按最多 256 字节读取连续线帧，每收到非空数据就刷新静默超时。该策略
允许 Windows 与 Jetson 的串口驱动以不同粒度交付字节，但不改变帧边界、
CRC 或 PayloadLength 规则。

主机只有在收到全部 4324 字节、通过帧 CRC、身份、配置哈希、采样数和质量
字段校验后，才能保存并报告成功。部分帧不得伪装成波形文件，也不得自动
触发第二次采集。

## 为产品化预留的扩展点

### 1. 传输适配器边界

帧源只暴露稳定段的地址、长度和当前段编号，不直接依赖 COM 端口、Windows
或 Jetson。TI USB CDC 是当前适配器；未来更换为其他 MCU USB 实现或设备侧
链路时，协议帧构造和采集缓冲不变。

### 2. 发送策略边界

当前策略是四段顺序异步发送和 BUSY 保留。未来可以在同一状态机上增加：

- 接口可用轮询和有界退避；
- 每段启动/完成超时；
- 发送字节数、BUSY 次数、重试次数和最后错误统计；
- 产品模式下的看门狗与租约联动。

这些策略不得改变线协议看到的连续 `CAPTURE_DATA` 字节序列。

### 3. 交付确认边界

现有帧已经包含 `capture_id`、`request_id`、`boot_id`、设备标识、配置哈希和
Sequence，可作为未来去重和交付确认的稳定身份。后续可以在 bridge/core
层增加 `CAPTURE_COMMITTED` 或等价确认，但 M3 不实现 MCU 持久缓存，也不
承诺断电后重传。

### 4. 重传边界

M3 仅允许在同一 USB 会话内、波形缓冲尚未释放时重新启动未被传输层接受的
当前段。未来若需要整帧重传，必须复用原 `capture_id` 和原始样本，不得把
重传实现成一次新的超声激励。

### 5. 周期采集与背压边界

当前只有单次采集。未来周期采集必须在进入下一次 ADC/DMA 前确认当前波形
缓冲已经被释放，或者显式引入第二缓冲。若主机消费速度不足，策略必须选择
停止调度、报告丢帧或使用 bridge 持久 spool，不能静默覆盖未交付数据。

### 6. bridge/core 持久化边界

MCU 负责生成并输出可验证的原始帧；bridge 负责设备字节流、临时交付和未来
spool；core 负责校验、SQLite 提交及向 BMS 上游提供数据接口。峰值、TOF、
能量、SOC/SOH 等分析仍不属于本采集模块。未来增强 bridge/core 不应要求
修改 ADC 样本布局。

### 7. 内存布局可替换性

当前保留“协议头、元数据、唯一波形缓冲、CRC”四个区域。未来若验证表明
单一连续帧缓冲更合适，可以将 DMA 目标移入连续帧的样本区，但必须保持
2048 个原始点、线协议和帧源接口不变。上层不依赖当前四段内存布局。

## M3 当前明确不实现

- 分块线协议、每块 ACK 或选择性重传；
- MCU 断电持久化和跨启动恢复；
- bridge 持久 spool 和 SQLite 提交确认；
- 多帧队列、双缓冲和连续周期采集；
- 自动重复 `CAPTURE_ONCE`；
- 网络 TLS、远程鉴权和产品级遥测平台。

这些能力有明确接入点，但不阻塞第一条真实波形。

## 验证与完成门禁

实现必须按测试先行完成以下验证：

1. 单元测试证明四个应用段的顺序和长度为 16、208、4096、4；
2. 注入一次 CDC BUSY，证明当前段不推进、不丢失且不触发新采集；
3. 注入发送完成事件，证明只提交对应在途段；
4. 断线或不可恢复错误使状态机终止，并保持安全状态；
5. 完整离线回归继续通过；
6. 真实硬件只在单独授权后执行一次 `Pulse=1`，主机必须收到完整 4324 字节；
7. 保存文件必须包含恰好 2048 个未经插值或修改的 `uint16` 原始点，且帧 CRC
   与设备返回一致。

只有第 6、7 项通过后，才能将 M3 首条 Windows 真实波形标记为完成。

## 方案取舍

本阶段不采用单一 4324 字节连续缓冲，因为它会把 DMA 目标偏移与当前协议
元数据布局耦合；也不保留 64 字节独立事务加完整 ACK 状态机，因为 TI CDC
已经负责端点分包，而产品级块确认会扩大当前范围。四段可提交状态机在不
复制波形的前提下，为当前跑通和未来可靠性增强提供了最小稳定边界。
